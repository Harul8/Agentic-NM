==============================================================================
1. System Goals
==============================================================================

Nyaymalaw runs a local-first legal chat system with:
- streaming responses over SSE
- structured fact collection before legal analysis
- analysis-ready handoff that supports either "proceed" or one last material fact
- grounded local retrieval from the vector store
- deterministic fallback behavior when generation is weak or grounding fails
- resumable chat state for mid-intake save and restore

The main product behavior is:
1. collect enough facts to understand the dispute
2. ask another clustered question if needed
3. once ready, move to grounded legal analysis
4. stream progress and text so the experience feels live

==============================================================================
1A. Conversation Principles
==============================================================================

Nyaymalaw should behave like a calm senior advocate doing real intake, not like
a chatbot form and not like a law lecture.

Intake style:
- begin with brief empathy or acknowledgment when the facts call for it
- identify the issue in plain human language
- explain why the next details matter
- ask 2 to 3 closely related questions together when they belong to one factual
  theme
- avoid scattered or abstract questionnaires
- move the case forward in small, meaningful factual clusters

What the intake should quietly assess:
- whether the factual account is internally coherent
- whether supporting material exists and what it currently proves
- whether the requested relief is presently supportable
- whether the urgency is real and what immediate posture exists

How that assessment should sound:
- never accuse the user of dishonesty
- never ask legal-conclusion questions back to the user
- prefer language such as:
  - these details will help me assess urgency
  - this will help me understand what can be properly supported on the record
  - I want to be careful not to overstate or understate the matter

Audience behavior:
- lay users should get plain English with minimal jargon
- legal professionals may get tighter legal phrasing, but still structured and clear

What intake should not do:
- cite statutes or case law from memory
- ask the user to repeat the whole story
- jump to final advice too early
- keep looping on the same unresolved point in awkward phrasing
- close randomly before the critical facts, evidence posture, and current stage
  are sufficiently clear

Meaningful completion:
- the intake should close only when the system has enough to move responsibly
  into grounded legal analysis
- if the user cannot add more on one final narrow point but the factual record is
  otherwise strong, the system may proceed rather than loop indefinitely

Final answer style:
- short fact framing
- grounded legal analysis
- practical next-step guidance
- flowing prose, not heading-heavy templated output

2. Top-Level Runtime Flow
==============================================================================

Frontend
  -> /submit_case/stream for the first user message
  -> /conversation/continue/stream for every later user turn
  -> /chats and /chats/{id} for save/load

Backend
  -> api_server.py receives the request
  -> services.interactive_chat.process_chat() orchestrates the phase
  -> services.fact_collector decides:
     - ask another intake question
     - or hand off to analysis
  -> services.response_generator_v2.generate_response() performs local retrieval
     and builds the final grounded opinion

The active architecture is a two-phase loop:

1. fact_collection
2. response_generation

==============================================================================
3. Current Request Lifecycle
==============================================================================

3.1 New legal case

User sends the first message.

Frontend:
- POST /submit_case/stream

Backend:
- api_server.py creates an SSE queue and worker thread
- process_chat(..., phase="fact_collection")
- fact_collector extracts a compact intake state
- system either:
  - returns the next clustered question
  - or marks the matter analysis-ready

If more facts are needed:
- frontend displays the next question
- workflow state remains in interview mode

If enough facts exist:
- backend returns the analysis-ready handoff prompt
- user may either say "proceed" or add one last material fact

3.2 Follow-up user turns

Frontend:
- POST /conversation/continue/stream

Backend:
- full conversation is passed into process_chat()
- the system no longer relies on the old qa_history-only interview protocol
- the same full-conversation path is used for both intake and post-intake turns

3.3 Analysis-ready handoff

This is a critical path.

If the immediately previous assistant turn is the analysis-ready prompt:
- the user does not re-enter intake
- the next user message is treated as either:
  - a confirmation to proceed
  - or one last material fact

The current implementation:
- builds facts from the actual user-history turns
- preserves the latest material fact in the analysis seed
- bypasses the old failure mode where the last fact was clipped or treated as a
  fresh case opening

3.4 Final grounded opinion

Backend switches to:
- phase="response_generation"

Then:
- generate_response() performs local retrieval
- local bare acts and case materials are formatted
- a grounded final answer is produced
- if draft generation fails grounding, the system falls back to a deterministic
  grounded response rather than a misleading empty result

6. Chat Orchestrator
==============================================================================

Primary file:
- services\interactive_chat.py

This is the central runtime controller.

Main responsibilities:
- sanitize and safety-check user input
- choose fact_collection or response_generation behavior
- route general chat away from legal analysis
- preserve context across turns
- handle the analysis-ready branch correctly

Important current rules:
- legal_opinion mode keeps the system on the legal path
- once the assistant has asked the analysis-ready prompt, the next user turn
  goes directly into response_generation
- "one last fact" is merged into the final facts summary rather than ignored

Current helper concepts:
- analysis-ready detection
- new-case detection
- user fact-history reconstruction
- chat-window summary augmentation

The biggest recent improvement in this file was:
- analysis-ready acknowledgment is processed before fresh-case detection
- base facts are rebuilt from user turns, not from assistant summaries

==============================================================================
7. Intake Engine
==============================================================================

Primary file:
- services\fact_collector.py

The intake engine is responsible for:
- compact state extraction
- legal vs generic routing
- next-question selection
- completion gating

Current design intent:
- one intake brain
- one next-question brain
- one completion rule
- then a predictable handoff into grounded analysis

Current intake behavior:
- asks 2 to 3 closely related questions within one factual theme
- tracks urgency, prior actions, evidence posture, and relief posture
- avoids restarting the case mid-stream
- filters noisy open points and low-quality questions

Completion behavior:
- complete when the normalized legal state is actually ready
- or when the user explicitly chooses to stop and enough facts exist

What the intake engine should not do:
- cite law from memory
- jump into final advice too early
- ask the same question repeatedly
- downgrade an ongoing legal matter into greeting or generic chat

==============================================================================
8. Response Generation
==============================================================================

Primary file:
- services\response_generator_v2.py

This module handles:
- local retrieval
- dispute construction for the fast path
- local grounding
- final opinion drafting
- deterministic fallback when needed

8.1 Interactive fast path

The active legal-opinion experience defaults toward a fast local path:
- local retrieval only
- warmed indexes and models
- compact grounded drafting
- streaming token output

The fast path now includes:
- focused fact compression that preserves late facts
- generic fact-alignment reranking of retrieved materials
- local-only rescue search if the first fast retrieval is empty
- safer grounded fallback when model output is rejected by the grounding guard

8.2 What is generalized vs what is heuristic

Generalized improvements:
- preserve first facts plus latest material fact
- score retrieved materials against the actual fact pattern
- retry broader local retrieval before giving up
- degrade to grounded fallback instead of false "no materials"

Heuristic boosts still exist:
- some dispute-pattern boosts for known failure modes
- for example, landlord lockout and rent-default are separated so the fast path
  does not over-collapse every tenancy dispute into rent arrears logic

The architecture should be read as:
- general retrieval path first
- targeted heuristics only as secondary boosts

8.3 Grounding guard

Generated text is checked against locally retrieved materials.

If the draft cites unsupported law:
- the answer is rejected
- the system now falls back to a deterministic grounded response based on local
  materials instead of incorrectly pretending nothing was found

9. Retrieval Architecture
==============================================================================

Primary file:
- retrieval\hybrid_retriever.py

The retrieval stack is local-first:
- FAISS semantic search
- BM25 lexical search
- reciprocal-rank fusion
- cross-encoder reranking

Current fast-path optimizations:
- preloaded indexes
- preloaded embedder
- preloaded reranker
- smaller candidate pools for interactive chat
- lower-latency fast search helpers:
  - search_bare_acts_fast()
  - search_case_summaries_fast()

The runtime also supports broader local search helpers as a second chance when
fast retrieval comes back thin.

This is now a runtime few-shot layer, not a training-only artifact.

Design:
- prompts stay light
- examples live outside the prompt strings
- runtime retrieves a small curated pack of high-quality examples

Used for:
- intake state extraction
- next-question behavior
- final opinion style

Important note:
- runtime few-shot retrieval should point only to the curated runtime pack
- it should not scan the full fine-tuning corpus during live requests

==============================================================================
14. Known Residual Quality Areas
==============================================================================

The system is materially better than the historical flow, but these remain the
main quality levers:

1. Intake quality
- some edge cases can still drift or ask an awkward next cluster

2. Retrieval relevance for niche possession / lockout disputes
- local materials are grounded, but not always as sharp as the fact pattern

3. Draft quality under grounding constraints
- some model drafts still over-cite or cite unsupported sections, forcing a
  deterministic fallback

These are quality improvements, not architecture blockers.
